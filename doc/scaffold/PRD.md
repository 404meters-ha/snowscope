# PRD · 脚手架生成功能（scaffold）

> 状态：✅ 定稿（2026-09-22，grilling 三轮共识）
> 下游文档：`architecture.md`（架构设计）→ `stories.md`（用户故事清单）→ 分期实现
> 变更规则：改需求先改这里，再同步下游文档。

## 1. 背景与目标

用户（单人开发者）的常见起点是一句话想法：「我想做个流放之路洗装备的工具」「我想做个 RSS 聚合站」。从想法到动手之间横着三段费时的活：找有没有现成框架、没有的话拆出需要哪些技术块再逐块找开源组件、最后把组件拼成一个能跑起来的项目。

本功能把这三段全链路自动化：

```
一句话需求
  → 整体框架匹配（适配度%）──采用──→ clone 地址 + 评估报告（终结）
        └─拆条─→ 技术条目确认 → 逐条开源选型 → Agent 生成可启动脚手架 zip
```

**价值**：
- 选型有依据：双轨适配度（规则可解释 + LLM 语义）+ 全链路调研文档留痕
- 组装零启动成本：产出的 zip 解压即能启动，不用从空目录开始
- 复用体系：四层缓存让重复需求/重复组合的边际成本趋近于零

**示例锚点**（贯穿全文档的参照用例）：「流放之路洗装备工具」→ 拆出 `鼠标操作`、`决策模型`、`视觉识别` 三条技术条目。

## 2. 用户与场景

- 单用户自用（`user_id=1`，无登录），部署形态与现有平台一致
- 场景 A：想验证「有没有人把轮子造好了」→ 整体匹配 → 采用，直接 clone
- 场景 B：没有合适的整体框架（需求太杂/太垂直）→ 拆条选组件 → 生成脚手架起步
- 需求域不设限（游戏工具、Web 系统、CLI、AI 应用……），检索与生成都不能假设领域

## 3. 功能需求

### FR-1 需求输入与整体框架匹配【V1】

- 输入：**一句话**（文本框，无结构化表单）
- 提交后跑后台任务：
  - 检索双通道：本地 `repos` 库优先（含 tags/精析数据）→ GitHub Search API 补充（`industry_pipeline` 同款模式，含限流降级）
  - 候选 5-8 个
  - 每候选产出**双轨适配度 0-100 + 理由**：
    - 规则分：语言/技术栈关键词匹配（用户技能画像 × 项目 language/topics）、活跃度
    - LLM 分：需求语义 vs 项目定位/README 摘要
- 结果面板附带 LLM 对需求的理解摘要；用户发现理解偏差可改话重跑

### FR-2 采用分支【V1】

- 候选中一键「采用」：给出该仓库 clone URL（可复制）+ 一份评估报告
- 评估报告：markdown 存库，前端抽屉查看（与贡献报告/行业报告同模式）
- 需求记录状态终结为 `done_adopt`

### FR-3 技术条目拆解与确认【V2】

- 平台原生 prompt（不接外部 skill）：一句话 → **3-8 条技术方案条目**
- 条目结构：编号、名称、职责描述、技术关键词
- 输出是结构化数据（非架构文档），直接入库
- **确认面板**：可增/删/改条目及其描述关键词；面板展示 LLM 推断的主技术栈（语言/运行时），可改
- 确认后才进入逐条选型

### FR-4 条目级选型【V2】

- 每条目 = 一次小型「行业洞察式」检索：关键词规划 → tags 归一（复用 `tags.ensure_tags`）→ 库内匹配 + GitHub Search → 候选 3-5 个
- 每候选双轨打分（同 FR-1 口径），逐条勾选
- **允许某条目不选任何开源项目**（默认行为）：标记「自研」，生成时该条目由 Agent 从零写骨架
- 全部条目选定后需求记录进入 `selected` 状态

### FR-5 Agent 生成脚手架【V3】

- 生成引擎：平台 Agent（in-process `agent_sdk`，与 /tech 同模式），**全自动、无模板**（需求域不设限，靠生成覆盖）
- 生成架构原则：**Agent 判断 base 框架**（优先整体匹配结果或条目选型中架构型项目）→ 其余组件作为模块/依赖挂载进 base
- 选中的开源项目落位**自动分层**：
  - 包型项目 → 进依赖清单（requirements.txt / package.json）
  - 应用型项目 → `vendor/` 目录或 clone 脚本 + 集成说明
  - 由 Agent 判断分层
- **zip 六件套**（缺一不可）：
  1. 可启动的代码骨架
  2. 前端页面（必有，作为项目入口或控制台）
  3. 行业调研文档（`docs/research.md`，全链路汇编：原始需求 → 框架对比 → 条目候选对比与选型理由 → 参考链接）
  4. 原始需求（一句话 + 系统归纳）
  5. 架构文档（条目清单 + 选型结果 + 集成关系）
  6. 各组件 license 清单（告警不阻断）
- **验收线（骨架可启动）**：解压 → 装依赖 → 一条命令启动 → 前端页面可打开、各模块接口位接好、核心逻辑留结构化 TODO（每处标明对应条目与参考开源项目）。不承诺功能可用。
- 操作：后台任务 + 任务面板进度；**失败一键重试**；改上游（条目/选型）后可**重新生成**

### FR-6 复用缓存【V3】

四层：
1. 项目数据复用：repo 元数据/README/精析结果（现有 `repos` 表，已有）
2. 适配度缓存：`(条目语义指纹, repo)` → 适配度结果
3. 拆解缓存：需求规范化指纹 → 条目清单（相似需求命中）
4. 产物缓存：组合指纹（条目 + 选型 + 版本）→ zip 产物，同组合重生成不重跑 Agent

### FR-7 需求记录与状态机【V1 起】

- 新表持久化每条需求及其全链路产出
- 状态机：`matched`（整体候选出）→ 分叉 `done_adopt` / `split`（条目确认）→ `selected`（选型完）→ `built`（zip 出）
- 卡片列表展示于新 tab，点开可断点续跑、可回退上游改完重跑

### FR-8 任务与 UI【V1 起】

- 新 tab「🏗 脚手架」：输入框 + 需求记录卡片列表 + 流程交互
- 交互三件套复用：解析确认对话框（条目确认）、focusTask 任务跟踪、报告抽屉
- 长任务挂现有 TaskManager（任务类型 `scaffold_match` / `scaffold_split` / `scaffold_select` / `scaffold_build`）

## 4. 非功能需求

- Agent 生成超时沿用 `skill_run_timeout`（默认 3600s）
- 成本意识：候选数受控（5-8 / 3-5）、缓存优先命中、串行 LLM 调用不并发扩
- **V3 技术验证门**：动工前先做一次 agent_sdk「生成可启动小项目」的能力验证；不过关则回到用户重谈生成方案
- GitHub 限流沿用现有识别与降级模式

## 5. 非目标（明确不做）

- 模板引擎生成（用户拍板：需求千奇百怪，模板覆盖不了）
- 外部架构拆解 skill 接入（澄清后：要的是结构化条目，原生 prompt 即可）
- 多开源项目的代码级融合（只做依赖化挂载 + 新写胶水代码）
- 功能可用级承诺（只到「骨架可启动」）
- license 阻断式检查、对外多用户分发

## 6. 里程碑

| 期 | 范围 | 验收 |
|---|---|---|
| V1 | FR-1/2/7/8 | 一句话 → 候选+适配度 → 采用得 clone 地址+报告；需求记录可续 |
| V2 | FR-3/4 | 拆条可编辑确认；逐条候选打分勾选 |
| V3 | FR-5/6 | zip 六件套满足「骨架可启动」验收线；四层缓存生效 |

每期独立可用、独立交付。

## 7. 风险

| 风险 | 缓解 |
|---|---|
| glm-4.7 单 Agent 生成质量上限 | 可重试、可迭代上游重生成；V3 前技术验证门 |
| 任意需求域的检索空结果 | GitHub Search 关键词由 LLM 规划（行业洞察同款）；允许条目自研兜底 |
| 生成耗时（10-30 分钟） | 后台任务 + 进度面板；产物指纹缓存避免重复生成 |
| GitHub 限流 | 现有限流识别 + 降级模式复用 |
